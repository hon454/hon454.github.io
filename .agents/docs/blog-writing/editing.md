# 블로그 글 윤문과 감사

기존 글의 의미와 목소리를 보존하면서 필요한 구간만 고친다. 일반적인 AI 티 제거를 별도 단계로 강제하지 않으며, 문맥과 저자 문체를 먼저 본다.

## 교정 범위

- 맞춤법만: 맞춤법, 띄어쓰기와 일반 단어의 명백한 오탈자만 고친다. 어미, 문장 길이와 순서를 바꾸지 않는다.
- 문장 윤문: 의미와 문단 순서를 유지하면서 번역투, 반복, 불필요한 형식 표현과 호흡을 국소적으로 고친다. 별도 요청이 없으면 이 범위를 사용한다.
- 구조 재편: 사용자가 명시했을 때만 문단 순서와 소제목을 바꾼다. 시간순 경험담과 문제 해결의 인과 순서를 임의로 재구성하지 않는다.
- 감사: 본문을 바꾸지 않고 문체 이탈, 사실 위험과 게시 전 확인 사항만 보고한다.

## 먼저 보존할 내용

윤문 전에 다음을 문맥 안에서 확인한다.

- 문장별 핵심 주장과 원인·조건·순서·비교 관계
- 부정, 예외, 범위와 판단 강도
- 직접 확인, 출처 기반, 추론의 구분
- 코드 블록, inline code, 오류 메시지와 기술 식별자
- 제품명, 파일명, 경로, 버전, 수치, 날짜, 단위, 직접 인용과 URL
- 프런트매터, Markdown 링크와 이미지 경로
- 기능적인 목록·소제목과 원문에 있는 짧은 유머

의심스러운 기술 표기는 자동으로 고치지 않는다. 본문 밖에서 원문과 제안 표기를 함께 보여 주고 확인을 요청한다.

## 우선 고칠 수 있는 표현

- `되어진다`, `보여질 수 있다` 같은 명백한 이중 피동·이중 완곡
- 범용 도입, 의례적인 결론과 홍보성·과장 표현
- 연결어미 바로 뒤의 불필요한 쉼표
- 가까운 문장에서 되풀이되는 결산 표현과 문두 접속사
- 문장마다 반복되는 이모지, 볼드와 인위적인 대구

다음 표현은 횟수만 세지 말고 실제 반복과 기능을 보고 판단한다.

- `통해`, `활용`, `사용`, `경우`, `할 수 있다`, `것이다`, `필요하다`
- 문두 접속사와 형식명사
- `-성`, `-적`, `-화`가 붙은 추상 표현
- 한글 뒤의 괄호 영어

동의어로 돌려 막아 표면 빈도만 낮추지 않는다. 필요 없는 표현을 삭제하거나 문장에 자연스럽게 흡수한다.

## 저자 문체로서 보존할 예외

- 기술 글의 `-다/-한다/-된다`체
- 추론에 필요한 `같다`, `보인다`, `가능성이 있다`와 출처를 나타내는 `~라고 한다`
- 재현 단계, 실행 순서, 선택지, 체크리스트와 실제 절 제목
- API, 클래스, 함수, 제품명, 표준 영어와 정착된 기술 용어
- 버전·예외·조건을 설명하는 기능적 괄호와 원문에 있던 짧은 대시·반문
- 자연스러운 시스템 동작 설명의 `된다`
- 짧은 해결 메모의 짧은 호흡과 개인 글의 기존 유머

## 문맥 기반 과윤문 방지

- 모든 의미 있는 변경에는 구체적인 이유가 있어야 한다.
- 원문이 이미 자연스러우면 고치지 않는 것이 올바른 결과다.
- 문장을 매끈하게 만들기 위해 주장 강도, 정보량과 개인적인 호흡을 평평하게 만들지 않는다.
- 한 문장을 고친 뒤 앞뒤 문맥에서 부정, 조건, 지시 대상과 시간 순서가 달라지지 않았는지 확인한다.
- 구조 재편에서는 이동한 내용과 실제로 삭제·추가한 내용을 구분해 검토한다.
- 같은 글을 다시 윤문했을 때 새로운 대규모 수정이 계속 생긴다면 이전 윤문을 재검토한다.

## 출력

- 윤문은 수정된 본문을 먼저 제시한다.
- 사실 확인이나 식별자 결정이 필요할 때만 `확인 필요`를 덧붙인다.
- 주요 편집 내역은 사용자가 요청했거나 의미에 영향을 줄 수 있는 변경이 있을 때만 짧게 설명한다.
- 감사에서는 문제 구간, 이유, 의미 훼손 위험과 권장 교정 범위만 보고한다. 보고서 형식을 채우려고 문제를 만들지 않는다.
