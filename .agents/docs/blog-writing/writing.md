# 블로그 글 작성

메모, 사실, 코드와 출처를 새 글로 만들 때 적용한다. 작성은 빈칸을 그럴듯하게 채우는 작업이 아니라 제공된 근거를 읽을 수 있는 글로 구성하는 작업이다.

## 입력 정리

작성 전에 입력을 다음처럼 구분한다. 누락된 항목을 채우려고 내용을 만들지 않는다.

- 글의 목적, 예상 독자와 목표 길이
- 반드시 포함할 사실과 주장
- 사용자가 직접 확인한 내용
- 출처가 제공된 내용
- 추론, 가설과 추천
- 원인, 조건, 순서, 비교처럼 명시된 관계
- 코드, 오류 메시지, 식별자, 버전, 수치, 날짜, 인용과 URL
- 제외할 내용
- 출력 상태: 초안 또는 게시 준비본. 생략되면 초안

두 사실이 함께 제공됐다는 이유로 새로운 인과관계를 만들지 않는다. 코드의 결과도 입력이나 실행 증거 없이 추정하지 않는다. 웹에서 확인한 사실을 사용자의 직접 경험처럼 쓰지 않는다.

## 글 유형

### 짧은 문제 해결 메모

입력이 짧거나 결과를 간결하게 남기려는 경우 기본값으로 사용한다.

`현상 또는 조건 → 바꾼 항목 → 확인된 결과`

필요한 절만 쓰고 소제목을 강제하지 않는다.

### 상세 문제 해결 글

환경, 재현, 원인과 제약 자료가 충분하거나 상세 글을 요청받았을 때 사용한다.

`현상 → 환경과 재현 조건 → 확인된 원인 또는 가능한 원인 → 해결 → 결과와 남은 제약 → 참고 자료`

자료가 없는 절은 생략한다.

### 기술 개념 설명 글

`개념과 실제 용도 → 비슷한 선택지 → 내부 동작 또는 사용법 → 코드와 예시 → 주의점과 선택 기준 → 참고 자료`

비교 대상이나 내부 동작 자료가 없으면 해당 절을 만들지 않는다.

### 개인 경험 글

`배경 → 기대나 관심사 → 예상 밖의 문제 → 당시 생각의 흐름 → 결과와 짧은 감상`

개인 경험 자료가 충분하지 않으면 사건이나 감정을 창작하지 않는다.

## 저장소에 글 만들기

- 글은 `src/content/posts/` 아래의 Markdown 또는 MDX 파일이다.
- 새 파일을 요청받으면 먼저 `src/content.config.ts`, 가까운 기존 글과 `pnpm new-post <filename>`의 결과를 확인한다. 생성 결과는 최종 규칙이 아니라 scaffold다. 파일명에서 만든 `title`, 실행일을 넣은 `published`, `draft: false`와 자동 생성한 `slug`를 각각 다시 검토한다.
- 일반 글은 `.md`를 사용하고 Astro나 Svelte 컴포넌트가 실제로 필요할 때만 `.mdx`를 사용한다.
- 파일명은 짧은 소문자 영문·숫자·하이픈을 우선한다. 이미 공개된 파일명은 링크 호환성을 고려해 임의로 바꾸지 않는다.
- 프런트매터는 현재 스키마와 가까운 글의 형식을 따른다. `title`과 `published`는 필수다. 사용자가 준 값을 우선하고, 새 초안에 발행일이 없으면 생성일을 임시 `published`로 둘 수 있지만 본문 밖에서 확인 대상으로 알린다. 다른 값도 추측해서 확정하지 않는다.
- `slug`는 Zod 스키마에는 없지만 loader가 원시 프런트매터에서 읽어 공개 URL의 ID로 사용하는 지원 필드다. 파일 경로와 다른 URL이 의도적으로 필요할 때만 두고, 파일 경로와 같은 자동 생성 값은 제거할 수 있다. 사용할 때는 짧은 소문자 영문·숫자·하이픈을 우선하며 중복과 기존 링크 영향을 확인한다.
- 초안으로 요청받았거나 게시 승인이 없으면 `draft: true`로 둔다. 생성 스크립트의 초기값이 게시 승인을 뜻하지는 않는다.
- 기존 `published`와 `updated`는 임의로 바꾸지 않는다. 맞춤법 교정이나 초안 작업만으로 `updated`를 갱신하지 않으며, 공개된 글의 실질적인 개정을 반영할 때는 사용자 요청이나 작업 맥락을 확인한다.
- `description`은 실제 글의 대상, 문제와 해결 범위를 구체적으로 요약한다. 본문에 없는 효익이나 결론을 추가하지 않는다.
- 사용자 요청 없이 게시, 배포, 발행일 변경과 외부 공유를 수행하지 않는다.

## 작성 원칙

1. 첫 부분에서 문제, 핵심 제약 또는 글의 실제 용도를 알 수 있게 한다.
2. 실제 코드·오류·설정 경로·재현 조건을 추상적인 교훈보다 앞세운다.
3. 입력에 근거가 있을 때만 장점과 함께 비용·제약·실패 조건을 쓴다.
4. 짧은 해결 확인은 짧게 끝낸다. 모든 문장을 완결형 해설로 늘이지 않는다.
5. 절차·선택지·체크리스트는 목록으로 유지하고, 단순 설명을 습관적으로 불릿화하지 않는다.
6. `-다`체를 유지하되 리듬을 위해 `~일 것이다`, `~할 수 있다`를 새로 넣지 않는다.
7. 실제 추론에는 필요한 완곡 하나를 남기고, 단정 가능한 사실을 습관적으로 흐리지 않는다.

## 선택적으로 덜어낼 AI식 표현

- 범용 도입, 의례적인 결론과 홍보성 형용사
- 반복되는 `결론적으로`, `요약하면`, `이는 ~을 의미한다`, `~라는 뜻이다`
- 문단마다 붙는 문두 접속사
- 같은 구조의 소제목·불릿·대구
- 불필요하게 반복되는 한글·영어 병기
- 문장마다 들어가는 굵은 글씨, 이모지와 장식적 대시

이 목록을 채점표나 금칙어 사전처럼 사용하지 않는다. 문맥상 필요한 표현과 기능적인 구조는 남긴다.

## 결과 상태

- 초안: 미확인 항목을 본문에 짧게 표시할 수 있다.
- 게시 준비본: 미확인 내용을 본문에 섞지 않고, 게시를 막는 항목을 본문 밖에 따로 기록한다.
- 저장소 파일을 변경했다면 본문 검토 뒤 프로젝트 지침에 맞는 콘텐츠 검사를 수행한다. 게시나 배포는 별도 요청이 있어야 한다.
