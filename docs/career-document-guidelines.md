# 경력 문서 작성 지침

이력서, 경력기술서, 포트폴리오와 프로젝트 글을 작성하거나 수정할 때 적용하는 이 블로그의 편집 기준이다. 채용 제출본은 해당 공고의 요구사항을 우선한다.

## 문서별 목적과 범위

### 이력서(Resume)

`src/content/spec/resume.md`

경력과 핵심 역량을 빠르게 파악하게 하는 요약 문서이자 전체 이력을 관리하는 기준 문서다. 연락처와 핵심 역량을 밝히고 경력, 기술 검증 프로젝트, 외부활동, 오픈소스, 수상, 학력, 자격, 교육과 외국어를 기록한다. 최근 경력과 대표 성과를 우선하고 오래된 경험은 짧게 정리한다. 경력별 성과는 CV로 연결한다.

### 경력기술서(CV)

`src/content/spec/cv.md`

이 블로그에서는 한국 채용에서 쓰는 경력기술서를 CV로 부른다. 재직 경력의 직무 역량과 성과를 증명하는 제출용 문서로, 이력서가 목차라면 경력기술서는 그 본문이다.

- **범위:** 정규직, 프리랜서, 인턴, 비고용 팀 활동과 군 복무의 개발 업무를 최신순으로 다룬다. 외부활동, 오픈소스, 수상, 학력과 자격은 이력서와 포트폴리오에서 관리한다.
- **구성:** 맨 위에 경력 요약과 핵심 역량을 두고, 회사 단위 아래에 프로젝트와 주요 업무를 배치한다. 회사 안에서는 중요도순으로 배치한다.
- **형식:** 주요 업무는 `과제`, `판단`, `수행`, `결과` 라벨의 개조식 목록으로 쓰고, 판단이 드러나지 않는 업무는 `판단`을 생략한다. 작은 경력은 라벨 없이 두세 개의 목록으로 쓴다. 한 업무 항목은 한 주제만 다루고, `결과`는 `과제`에서 제기한 문제에 답한다. 문장은 명사형으로 끝맺는다.
- **내용:** 기술 선택의 근거와 검토한 대안, 협업 대상과 본인 담당 범위를 밝힌다. 사내 코드명과 외부 서비스명에는 처음 언급할 때 짧은 설명을 붙인다. 결과는 확인된 수치나 관찰된 변화로 쓰고, 수치가 없으면 바뀐 구조, 표준화된 절차와 업무 범위로 대신한다.
- **분량:** A4 3~4장을 목표로 한다. 클래스명과 자료구조 같은 구현 세부는 프로젝트 글로 연결하며, 전체 기능 목록이나 개발 일지로 만들지 않는다.

### 포트폴리오(Portfolio)

`src/content/spec/portfolio.md`

대표 작업을 선별해 결과물과 근거로 역량을 보여주는 문서다. 화면, 영상, 데모, 공개 코드와 설계 자료에 작업을 이해하는 데 필요한 맥락, 본인의 기여와 결과를 붙인다. 수상과 동료 추천은 이를 보충하는 자료로 배치한다. 전체 경력을 나열하지 않으며 상세 사례는 프로젝트 글로 연결한다.

기술 검증 프로젝트는 특정 기술 역량을 측정하거나 검증하려고 진행하는 개인 프로젝트로, 도입부 바로 다음의 최상단 섹션에 둔다. 다른 사람이 사용하는 도구나 라이브러리는 오픈소스 프로젝트로 구분한다. 프로젝트마다 소개, 진행 기간, 주요 기술을 담은 표와 짧은 소개 문단만 두고, 결과 수치와 단계별 상세 내용은 쓰지 않는다. 상세 내용은 공개 저장소의 README로 연결하며, 저장소 링크는 프로젝트 소제목에 둔다.

회사 섹션은 `주요 경력` 상위 섹션 아래에 둔다. 회사 정보는 소속 기간, 참여 형태, 담당 직무를 담은 표로 통일한다. 회사 내 모든 프로젝트에는 참여 기간과 주요 기술을 담은 표를 둔다.

오픈소스 프로젝트는 유지관리자(Maintainer)와 기여자(Contributor)로 구분하고, 각 역할 아래에 프로젝트를 배치한다. 프로젝트 소개와 주요 기술은 표로, 본인의 주요 작업은 대시 목록으로 작성하고 결과물이나 기여 PR로 연결한다. 회사 정보나 참여 기간 항목은 일률적으로 요구하지 않는다.

오픈소스 저장소 링크는 프로젝트 소제목에, 상세 설명과 배포 링크는 관련 작업 항목에 배치한다. 기여 PR은 해당 작업의 굵은 제목에 연결하며, 프로젝트 아래에 별도의 링크 목록을 나열하지 않는다.

프로젝트 표에는 작업을 이해하는 데 필요한 짧은 소개를 포함할 수 있다. 주요 기여는 빠르게 훑어볼 수 있는 목록으로 선별하되, 프로젝트마다 항목 수와 분량을 동일하게 강제하지 않는다. 대표 자료에는 확인할 내용과 본인의 기여 범위를 설명하고, 제품 소개 자료와 구현 또는 성과의 근거를 구분한다. 자료를 접기(`<details>`) 안에 숨기지 않는다. 대표 자료는 본문에 보이게 두고, 보조 자료는 프로젝트 글의 해당 섹션으로 연결한다.

### 프로젝트 글

`src/content/projects/`

개별 프로젝트의 상세 사례와 근거를 기록한다. 제품 설명과 참여 범위를 밝히고, 경력기술서와 포트폴리오에서 요약한 작업의 구현 과정과 자료를 깊게 다룬다. `/projects/`는 전체 작업 목록, `/portfolio/`는 대표 작업의 선별 목록으로 운영한다.

## 공통 작성 규칙

경력기술서와 포트폴리오는 회사나 소속을 상위 섹션으로, 프로젝트나 담당 업무를 하위 섹션으로 구성한다. 소속과 역할, 참여 형태는 회사 단위로 적고 프로젝트별 기간과 기술을 하위에 둔다. 회사 단위 직무명은 고용된 곳이면 실제 직함을, 비고용 팀 활동이면 실제로 맡은 역할을 쓰고 모든 문서에서 같게 유지한다. 프로젝트 역할은 그 프로젝트에서 실제로 한 일을 쓴다. 이력서와 포트폴리오에서 기술 검증 프로젝트, 외부활동과 개인 오픈소스는 경력과 별도의 상위 섹션으로 구분한다.

1. **독립성:** 각 문서 안에서 경력이나 작업의 핵심을 이해할 수 있게 쓴다. 링크는 상세 설명을 보충하는 데 사용한다.
2. **선별:** 블로그 문서는 범용 경력 소개로 유지하고, 특정 공고에 제출할 때는 직무와 관련된 경험을 우선한다. 모든 프로젝트에 같은 분량이나 형식을 강제하지 않는다.
3. **기여:** 팀의 결과와 본인이 담당한 일을 구분한다. 사용 기술은 실제 적용 업무와 연결해 설명한다.
4. **근거:** 역할, 성과, 선택 이유는 원자료나 사용자 확인에 근거한다. 수치는 측정 범위와 조건을 확인하며, 미확인 효과와 인과관계를 만들지 않는다. 자료를 재구성한 경우 실제 제품 화면이나 소스와 구분한다.
5. **중복과 일관성:** 전체 이력은 이력서를 기준으로 관리하고 다른 문서는 목적에 맞게 선별한다. 한 문서에서 내용을 줄일 때는 그 내용이 목적에 맞는 다른 문서에 남아 있는지 확인한다. 같은 경험과 사실은 반복할 수 있지만 긴 문단을 그대로 복제하지 않는다. 사실을 수정하면 관련 문서의 기간, 역할, 수치와 기여 범위도 대조해 반영한다. 문서 간 충돌은 원자료와 사용자 확인으로 해결한다.
6. **표현:** 구체적인 행동과 결과를 간결하게 쓴다. 한 문장과 한 목록 항목에는 한 주제만 담는다. 같은 대상은 모든 문서에서 같은 용어로 부른다. 명사를 길게 이어 붙이지 않고 조사와 서술어로 풀어 쓴다. '~도 했습니다', '~도 구현했습니다' 식의 덧붙임을 반복하지 않는다. 가운뎃점 대신 쉼표나 접속 표현을 쓴다.
7. **완료 확인:** 문서 목적에 맞는 내용인지, 개인 기여와 근거가 명확한지, 불필요한 반복이 없는지 확인하고 링크와 미디어의 표시를 검증한다.
