# 경력 문서 작성 지침

이력서, 경력기술서, 포트폴리오와 프로젝트 글을 작성하거나 수정할 때 적용하는 이 블로그의 편집 기준이다. 채용 제출본은 해당 공고의 요구사항을 우선한다.

## 문서별 목적과 범위

### 이력서

`src/content/spec/resume.md`

경력과 직무 적합성을 빠르게 파악하게 한다. 연락처, 핵심 역량, 소속과 기간, 역할과 대표 성과, 기술, 학력과 자격을 요약한다. 상세 구현 과정은 연결 문서에 둔다.

### 경력기술서

`src/content/spec/career.md`

실제 업무 수행 능력과 개인의 기여를 설명한다. 회사와 프로젝트별 담당 범위를 밝히고, 대표 업무의 문제와 제약, 본인의 판단과 실행, 확인된 결과를 설명한다. 전체 기능 목록이나 개발 일지로 만들지 않는다.

### 포트폴리오

`src/content/spec/portfolio.md`

선별한 작업으로 역량을 입증한다. 대표 결과물에 프로젝트 맥락, 본인의 기여와 결과를 짧게 붙인다. 화면, 영상, 데모, 공개 코드, 설계 자료 등 작업에 맞는 근거를 제시하고 상세 사례로 연결한다.

### 프로젝트 글

`src/content/projects/`

개별 작업의 상세 사례와 근거를 제공한다. 제품 설명, 참여 범위, 구현 과정과 결과물을 프로젝트 성격에 맞게 기록한다. `/projects/`는 전체 목록, `/portfolio/`는 대표 작업의 선별 목록으로 운영한다.

## 공통 작성 규칙

1. **독립성:** 각 문서 안에서 경력이나 작업의 핵심을 이해할 수 있게 쓴다. 링크는 상세 설명을 보충하는 데 사용한다.
2. **선별:** 블로그 문서는 범용 경력 소개로 유지하고, 지원용 문서는 직무와 관련된 경험을 우선한다. 모든 프로젝트에 같은 분량이나 형식을 강제하지 않는다.
3. **기여:** 팀의 결과와 본인이 담당한 일을 구분한다. 사용 기술은 실제 적용 업무와 연결해 설명한다.
4. **근거:** 역할, 성과, 선택 이유는 원자료나 사용자 확인에 근거한다. 수치는 측정 범위와 조건을 확인하며, 미확인 효과와 인과관계를 만들지 않는다. 자료를 재구성한 경우 실제 제품 화면이나 소스와 구분한다.
5. **중복:** 기간, 역할과 대표 성과는 반복할 수 있다. 긴 설명은 목적에 맞는 문서에 두고 다른 문서에서는 요약과 링크로 연결한다. 기본 이력은 이력서, 수행 과정은 경력기술서, 상세 자료는 프로젝트 글에서 관리한다.
6. **일관성:** 사실을 수정하면 관련 문서의 기간, 역할, 수치와 기여 범위도 대조한다. 문서 간 충돌은 원자료와 사용자 확인으로 해결한다.
7. **표현:** 구체적인 행동과 결과를 간결하게 쓴다. '~도 했습니다', '~도 구현했습니다' 식의 덧붙임을 반복하지 않는다. 가운뎃점 대신 쉼표나 접속 표현을 쓴다.
8. **완료 확인:** 문서 목적에 맞는 내용인지, 개인 기여와 근거가 명확한지, 불필요한 반복이 없는지 확인하고 링크와 미디어의 표시를 검증한다.
