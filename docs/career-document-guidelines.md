# 경력 문서 작성 지침

이력서, 경력기술서, 포트폴리오와 프로젝트 글을 작성하거나 수정할 때 적용하는 이 블로그의 편집 기준이다. 채용 제출본은 해당 공고의 요구사항을 우선한다.

## 문서별 목적과 범위

### 이력서(Resume)

`src/content/spec/resume.md`

경력과 핵심 역량을 빠르게 파악하게 하는 요약 문서다. 연락처와 핵심 역량을 밝히고, 최근 경력과 대표 성과를 우선한다. 학력과 자격, 외부활동은 중요도에 따라 선별하고 오래된 경험은 짧게 정리한다. 상세 경력은 CV로 연결한다.

### 경력기술서(CV)

`src/content/spec/cv.md`

이 블로그에서는 전체 이력과 상세 경력을 관리하는 문서를 CV로 부른다. 회사와 프로젝트별 담당 범위를 밝히고, 주요 업무의 문제와 제약, 본인의 판단과 실행, 확인된 결과를 설명한다. 학력, 자격, 교육, 수상, 외부활동과 오픈소스 경험을 함께 기록한다. 전체 기능 목록이나 개발 일지로 만들지 않는다.

### 포트폴리오(Portfolio)

`src/content/spec/portfolio.md`

대표 작업을 선별해 결과물과 근거로 역량을 보여주는 문서다. 화면, 영상, 데모, 공개 코드와 설계 자료에 작업을 이해하는 데 필요한 맥락, 본인의 기여와 결과를 붙인다. 수상과 동료 추천은 이를 보충하는 자료로 배치한다. 전체 경력을 나열하지 않으며 상세 사례는 프로젝트 글로 연결한다.

회사 정보는 소속 기간, 참여 형태, 담당 직무를 담은 표로 통일한다. 회사 내 모든 프로젝트에는 참여 기간과 주요 기술을 담은 표를 둔다.

오픈소스 프로젝트는 유지관리자(Maintainer)와 기여자(Contributor)로 구분하고, 각 역할 아래에 프로젝트를 배치한다. 프로젝트 소개와 주요 기술은 표로, 본인의 주요 작업은 대시 목록으로 작성하고 결과물이나 기여 PR로 연결한다. 회사 정보나 참여 기간 항목은 일률적으로 요구하지 않는다.

오픈소스 저장소 링크는 프로젝트 소제목에, 상세 설명과 배포 링크는 관련 작업 항목에 배치한다. 기여 PR은 해당 작업의 굵은 제목에 연결하며, 프로젝트 아래에 별도의 링크 목록을 나열하지 않는다.

프로젝트 표에는 작업을 이해하는 데 필요한 짧은 소개를 포함할 수 있다. 주요 기여는 빠르게 훑어볼 수 있는 목록으로 선별하되, 프로젝트마다 항목 수와 분량을 동일하게 강제하지 않는다. 대표 자료에는 확인할 내용과 본인의 기여 범위를 설명하고, 제품 소개 자료와 구현 또는 성과의 근거를 구분한다.

### 프로젝트 글

`src/content/projects/`

개별 프로젝트의 상세 사례와 근거를 기록한다. 제품 설명과 참여 범위를 밝히고, 포트폴리오에서 요약한 작업의 구현 과정과 자료를 깊게 다룬다. `/projects/`는 전체 작업 목록, `/portfolio/`는 대표 작업의 선별 목록으로 운영한다.

## 공통 작성 규칙

경력기술서와 포트폴리오는 회사나 소속을 상위 섹션으로, 프로젝트나 담당 업무를 하위 섹션으로 구성한다. 소속과 역할, 참여 형태는 회사 단위로 적고 프로젝트별 기간과 기술을 하위에 둔다. 외부활동과 개인 오픈소스는 별도 상위 섹션으로 구분한다.

1. **독립성:** 각 문서 안에서 경력이나 작업의 핵심을 이해할 수 있게 쓴다. 링크는 상세 설명을 보충하는 데 사용한다.
2. **선별:** 블로그 문서는 범용 경력 소개로 유지하고, 지원용 문서는 직무와 관련된 경험을 우선한다. 모든 프로젝트에 같은 분량이나 형식을 강제하지 않는다.
3. **기여:** 팀의 결과와 본인이 담당한 일을 구분한다. 사용 기술은 실제 적용 업무와 연결해 설명한다.
4. **근거:** 역할, 성과, 선택 이유는 원자료나 사용자 확인에 근거한다. 수치는 측정 범위와 조건을 확인하며, 미확인 효과와 인과관계를 만들지 않는다. 자료를 재구성한 경우 실제 제품 화면이나 소스와 구분한다.
5. **중복과 일관성:** 전체 이력은 CV를 기준으로 관리하고 다른 문서는 목적에 맞게 선별한다. 같은 경험과 사실은 반복할 수 있지만 긴 문단을 그대로 복제하지 않는다. 사실을 수정하면 관련 문서의 기간, 역할, 수치와 기여 범위도 대조해 반영한다. 문서 간 충돌은 원자료와 사용자 확인으로 해결한다.
6. **표현:** 구체적인 행동과 결과를 간결하게 쓴다. '~도 했습니다', '~도 구현했습니다' 식의 덧붙임을 반복하지 않는다. 가운뎃점 대신 쉼표나 접속 표현을 쓴다.
7. **완료 확인:** 문서 목적에 맞는 내용인지, 개인 기여와 근거가 명확한지, 불필요한 반복이 없는지 확인하고 링크와 미디어의 표시를 검증한다.
