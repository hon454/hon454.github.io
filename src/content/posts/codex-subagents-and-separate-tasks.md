Codex에서 다른 에이전트에게 업무를 맡길 때는 현재 작업의 서브에이전트를 만들 수도 있고, 별도 앱 작업을 생성할 수도 있다. 두 방식 모두 자기 대화 맥락에서 실행되며 모델과 추론 수준을 지정할 수 있다. 이 공통점만 보면 이름만 다른 기능처럼 보이기 쉽다.

혼동을 풀려면 몇 가지를 나눠 봐야 한다. 스레드와 에이전트가 같은 대상을 가리키는지, 맥락을 나눈다는 것이 파일까지 격리한다는 뜻인지, 모델을 따로 고를 수 있다는 사실이 두 방식의 차이를 없애는지다. 용어에서 출발해 실제 도구의 동작을 확인하면, 어떤 단위로 일을 맡길지 판단할 수 있다.

:::note[확인 기준]
이 글은 2026년 9월 11일에 확인한 공식 문서와 Codex 데스크톱 환경의 도구 명세를 기준으로 한다. 도구 이름과 인자, 지원 범위는 실행 환경에 따라 달라질 수 있다.
:::

## 작업, 채팅, 스레드는 무엇이 다른가

앱에서는 대화 항목 하나를 작업, 채팅, 스레드라고 부르기도 한다. 같은 항목을 가리키더라도 강조하는 대상은 다르다. 작업은 달성할 결과, 채팅은 대화 공간, 스레드는 그 기록을 담는 기술적 객체에 가깝다.

| 용어 | 의미 | 예시 |
| --- | --- | --- |
| 작업(task) | 달성할 결과 또는 앱의 작업 항목 | 검색 기능 개선 |
| 채팅(chat) | 메시지와 결과가 쌓이는 대화 공간 | 검색 기능을 논의하는 대화 |
| 스레드(thread) | 대화 기록과 턴을 담는 객체 | `threadId`로 지정하는 대상 |
| 턴(turn) | 요청과 그에 따른 실행 | 오류 조사부터 답변까지 |
| 에이전트(agent) | 판단하고 도구를 사용하는 주체 | 주 에이전트, 서브에이전트 |
| 모델(model) | 판단·응답에 쓰는 AI 모델 | 에이전트에 지정한 GPT 모델 |

공식 [용어집](https://learn.chatgpt.com/docs/glossary)은 task를 달성할 결과, thread를 대화 기록을 담는 기술적 객체로 설명한다. [App Server 문서](https://learn.chatgpt.com/docs/app-server#core-primitives)에서는 thread가 turn을 포함하고, turn 안에는 메시지·명령 실행·도구 호출 같은 item이 들어간다고 정의한다.

스레드와 에이전트도 구별된다. 스레드는 기록을 담고, 에이전트는 그 맥락에서 판단하고 도구를 사용한다. 따라서 스레드가 하나 생겼다는 설명만으로 그 에이전트가 누구에게 업무를 받았고 결과를 어디로 돌려주는지까지 알 수는 없다.

이 글에서는 앱에서 따로 만드는 대화를 ‘별도 작업’, `threadId` 같은 기술적 대상을 설명할 때는 ‘스레드’라고 부른다. 여기서 스레드는 운영체제의 실행 스레드와는 다른 뜻이다.

### 위임·조율·오케스트레이션의 구분

일부 일을 다른 에이전트에게 맡기는 것은 위임(delegation)이다. 담당 범위와 순서를 맞추거나 진행 중인 작업에 추가 정보를 전달하는 것은 조율(coordination)이라고 부를 수 있다.

이 일을 나누고, 맡기고, 기다리고, 결과를 검토해 합치는 전체 과정을 오케스트레이션(orchestration)이라고 한다. Codex의 [서브에이전트 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents#orchestration-and-thread-controls)에서도 에이전트 생성, 후속 지시 전달, 결과 대기 등을 이 표현으로 설명한다.

오케스트레이터는 이 과정을 관리하는 역할이며, 특정 모델을 가리키는 이름은 아니다. 전체 이슈의 진행을 관리하고 하위 업무를 배정하는 에이전트가 이 역할을 수행한다.

에이전트 하나가 여러 일을 순서대로 하거나 검색 도구를 여러 개 호출하는 것만으로 멀티에이전트가 되는 것은 아니다. 일을 맡아 자기 맥락에서 판단하는 에이전트를 따로 두었는지가 중요하다.

## 서브에이전트에도 스레드가 있다면 무엇이 다른가

서브에이전트는 전달받은 업무와 대화를 바탕으로 자기 맥락에서 실행된다. 부모의 대화를 실시간으로 전부 공유하는 구조는 아니다.

공식 문서에서도 서브에이전트가 일하는 공간을 [agent thread](https://learn.chatgpt.com/docs/agent-configuration/subagents#core-terms)라고 부른다. 지원하는 클라이언트에서는 그 스레드를 열어 진행 상황과 결과를 볼 수 있다. 서브에이전트에는 대화가 없다거나, 내용을 전혀 들여다볼 수 없다는 구분은 맞지 않는다.

별도 작업도 자기 스레드에서 실행된다. 따라서 두 방식을 ‘대화가 있는 쪽과 없는 쪽’으로 나눌 수는 없다. 구분에 필요한 것은 부모와의 관계, 초기 맥락의 전달 방식, 결과를 수집하는 경로다.

| 비교 항목 | 현재 작업의 서브에이전트 | 별도 앱 작업 |
| --- | --- | --- |
| 관계 | 부모가 위임한 하위 업무 | 따로 이어가는 앱 작업 |
| 초기 맥락 | 업무와 선택한 범위의 부모 대화 | 새 프롬프트 또는 대화 분기 |
| 결과 전달 | 부모에게 최종 답변 전달 | 조율 작업이 도구로 수집 |
| 후속 지시 | 부모의 메시지·추가 업무 | 직접 대화 또는 작업 간 메시지 |
| 파일 환경 | 현재 세션은 같은 폴더 공유 | Local 또는 별도 worktree 등 |
| 분담 단위 | 현재 목표의 일부 | 개별 완료 기준을 가진 일 |

![서브에이전트는 최종 답변을 부모에게 전달하고, 별도 작업은 조율 작업이 도구로 결과를 수집하는 흐름](./images/codex-subagents-and-separate-tasks/delegation.svg)

서브에이전트에 맡긴 검토는 최종 답변이 부모에게 돌아오면서 현재 작업의 판단으로 이어진다. 별도 검토 작업은 자체 대화로 남고, 조율 작업이 그 결과를 읽어 가져온다. 위 도표는 이 업무와 결과의 흐름을 나타낸다.

두 방식이 할 수 있는 일은 상당히 겹친다. 별도 작업을 만들었다고 모델의 능력이 높아지는 것도 아니고, 서브에이전트라고 반드시 짧은 조사만 해야 하는 것도 아니다.

## 도구에서 드러나는 관계와 맥락의 차이

이 관계의 차이는 업무를 만들고 후속 지시를 보내는 도구에서도 드러난다. 아래는 확인한 Codex 환경의 호출 형태이며, 앱 입력창에서 실행하는 명령어나 공개 API의 요청 규격은 아니다.

### 서브에이전트에 위임하기

현재 환경의 서브에이전트 도구는 `collaboration` 네임스페이스에 있다.

| 도구 | 역할 |
| --- | --- |
| `spawn_agent` | 서브에이전트를 생성하고 첫 업무를 배정한다. |
| `send_message` | 메시지를 전달한다. 새 턴은 시작하지 않는다. |
| `followup_task` | 추가 업무를 배정한다. 쉬고 있다면 새 턴을 시작한다. |
| `list_agents` | 에이전트 트리와 상태를 확인한다. |
| `wait_agent` | 메시지나 완료 알림을 기다린다. |
| `interrupt_agent` | 진행 중인 턴을 중단한다. 후속 지시는 가능하다. |

`send_message`와 `followup_task`는 구별할 필요가 있다. 조사 중인 에이전트에게 “모바일도 확인해 달라”고 보충하는 것과, 조사를 끝낸 에이전트에게 “이제 수정안을 작성해 달라”고 다시 일을 시키는 것은 다르다. 뒤의 경우에는 새 실행을 시작시키는 후속 업무가 필요하다.

공개 [Responses API의 멀티에이전트 문서](https://developers.openai.com/api/docs/guides/responses-multi-agent#how-multi-agent-works)에도 같은 이름의 여섯 협업 동작이 나온다. 아래 코드는 현재 Codex 도구의 호출 예시다. 공개 API의 요청 규격이나 뒤의 실험에 사용한 프롬프트와는 구분해야 한다.

```javascript
collaboration.spawn_agent({
  task_name: "reviewer",
  fork_turns: "none",
  model: "gpt-5.6-terra",
  reasoning_effort: "high",
  message:
    "현재 작업 디렉터리에서 변경 사항을 검토해줘. " +
    "파일은 수정하지 말고, 재현 가능한 버그와 파일 위치를 보고해줘."
});
```

`message`는 업무, `model`은 사용할 모델, `reasoning_effort`는 추론 수준을 지정한다. `task_name`을 `reviewer`로 정하는 것만으로 검토 기준이 설정되지는 않는다. 무엇을 보고 어떤 결과를 돌려줄지는 업무 메시지에서 설명해야 한다.

여기서 맥락 상속과 모델 선택을 같은 설정으로 이해하면 혼동이 생긴다. `fork_turns`는 부모의 기존 대화를 얼마나 전달할지 정하고, `model`과 `reasoning_effort`는 실행할 모델과 추론 수준을 정한다. 개념은 구별되지만 현재 도구에서는 두 설정 사이에 제약이 있다.

| `fork_turns` | 대화 전달 | 현재 도구에서 모델·추론 재지정 |
| --- | --- | --- |
| 생략 또는 `"all"` | 기존 대화 전체 상속 | 부모 설정을 상속하며 재지정 불가 |
| `"none"` | 기존 대화 전달 안 함 | 지정 가능 |
| `"3"` 같은 양의 정수 문자열 | 최근 지정 범위의 턴 전달 | 지정 가능 |

이 환경에서 부모 대화를 전부 상속하면 모델 설정도 함께 상속한다. 다른 모델을 쓰려면 전달할 턴을 선택하거나 필요한 요구사항을 메시지로 정리해야 한다. 반대로 `"none"`은 부모의 기존 대화 기록을 넘기지 않는다는 뜻이며, 지침이나 도구까지 없는 상태를 의미하지는 않는다.

일반적인 Codex 설정에서는 `[agents]` 기본값이나 사용자 정의 에이전트 파일의 `model`, `model_reasoning_effort`도 사용할 수 있다. 위 표는 모든 Codex 버전에 공통인 규칙으로 보기보다, 호출할 때 실제 명세를 확인해야 하는 사례로 이해하는 편이 맞다. [공식 모델·추론 설정 문서](https://learn.chatgpt.com/docs/agent-configuration/subagents#choosing-models-and-reasoning)도 별도로 참고할 수 있다.

### 별도 작업을 만들고 조율하기

별도 앱 작업에는 `mcp__codex_app__`로 시작하는 도구를 사용한다. 표에서는 접두사를 생략했다.

| 도구 | 역할 |
| --- | --- |
| `list_projects` | 프로젝트와 Git 저장소 여부를 확인한다. |
| `create_thread` | 별도 작업을 생성한다. |
| `send_message_to_thread` | 해당 작업에 후속 프롬프트를 보낸다. |
| `wait_threads` | 지정한 작업의 완료나 주의가 필요한 상태를 기다리거나 확인한다. |
| `read_thread` | 작업의 대화와 실행 요약을 읽는다. |
| `fork_thread` | 기존 작업의 완료된 대화 기록에서 새 작업을 분기한다. |

별도 검토 작업을 만든다면 호출 형태는 다음과 같다. 프로젝트 ID와 검토 대상은 실제 값으로 바꿔야 한다.

```javascript
mcp__codex_app__create_thread({
  title: "검색 기능 검토",
  prompt:
    "검색 기능 변경을 검토해줘. " +
    "검토 대상 커밋, 요구사항과 완료 기준: ...",
  model: "gpt-5.6-terra",
  thinking: "high",
  target: {
    type: "project",
    projectId: "<list_projects로 확인한 ID>",
    environment: {
      type: "worktree",
      startingState: {
        type: "branch",
        branchName: "<실제로 검토할 브랜치>"
      }
    }
  }
});
```

별도 작업도 모델과 추론 수준을 지정할 수 있다. 추론 수준의 인자 이름은 `thinking`이며, 서브에이전트의 `reasoning_effort`와 대응한다. 다만 생략했을 때의 기준은 다르다. 현재 앱 도구는 사용자가 설정한 새 작업의 기본 모델을 사용하므로 부모 모델을 상속한다고 가정하면 안 된다.

작업 생성도 비동기다. 생성 요청이 성공한 것과 검토가 끝난 것은 다르다. Worktree를 준비 중이면 `clientThreadId`가 먼저 반환될 수 있으며, 이것을 `threadId`가 필요한 후속 도구에 그대로 넘기면 안 된다. 준비된 작업의 `threadId`를 확보한 뒤 상태를 확인하고 메시지를 보낸다.

```javascript
mcp__codex_app__send_message_to_thread({
  threadId: "<준비된 작업의 ID>",
  prompt: "검색어가 비어 있을 때의 동작도 확인해줘."
});
```

후속 메시지에서는 `model`과 `thinking`을 생략하면 해당 작업의 기존 설정을 유지한다. 필요하면 이 필드로 설정을 변경할 수 있다.

새 작업 생성과 대화 분기도 구별된다. `create_thread`는 새 초기 프롬프트로 시작한다. `fork_thread`는 기존 대화 기록을 바탕으로 분기하며, 현재 앱 도구는 진행 중인 미완료 턴을 복사하지 않는다. 공개 [App Server 문서](https://learn.chatgpt.com/docs/app-server#start-or-resume-a-thread)에서도 `thread/start`와 `thread/fork`를 별도로 설명한다.

## 맥락이 나뉘면 파일도 격리되는가

서브에이전트든 별도 작업이든 대화 맥락은 나뉠 수 있다. 하지만 이것만으로 서로 다른 코드 사본에서 작업한다고 볼 수는 없다. 파일 환경의 분리는 별도로 확인해야 한다.

이 글을 준비한 환경의 서브에이전트는 같은 작업 디렉터리를 공유한다. 한 에이전트가 파일을 수정하면 다른 에이전트도 수정된 파일을 읽는다. 하지만 파일을 바꾼 이유나 새로 전달된 요구사항까지 실시간으로 모두 공유하는 것은 아니다.

별도 작업도 같은 로컬 폴더를 사용하면 파일 변경이 서로 영향을 줄 수 있다. 작업을 새로 만들었다는 사실만으로 코드가 격리되지는 않는다.

Worktree를 사용하면 별도 체크아웃에서 변경을 진행할 수 있다. 서로 독립적인 구현을 동시에 하기에는 유리하지만, 작업마다 환경을 준비하고 나중에 변경을 통합해야 한다. 같은 인터페이스를 서로 다르게 수정했다면 합칠 때 조정이 필요하다. Worktree가 설계의 충돌까지 해결해 주지는 않는다. [공식 Worktree 문서](https://learn.chatgpt.com/docs/environments/git-worktrees)는 병렬 작업을 위한 변경 격리와 Local 사이의 이동을 설명한다.

## 구분한 개념을 작업 선택에 적용하기

작업 관계와 파일 환경을 구분하면 선택 기준도 구체적이 된다. 현재 목표를 위한 독립적인 조사나 검토라면 서브에이전트가 편하다. 주 에이전트가 필요한 부분을 맡기고 결과를 받아 같은 대화에서 판단할 수 있다. 긴 탐색 과정은 다른 맥락에서 진행하고 주 대화에는 필요한 결과를 남길 수 있다. 공식 문서에서도 [읽는 비중이 높은 작업부터 병렬 위임을 적용](https://learn.chatgpt.com/docs/agent-configuration/subagents#why-subagent-workflows-help)하도록 제안한다.

다만 필요한 조건을 빠뜨리면 서브에이전트는 그 조건을 모르는 상태에서 일한다. 돌아오는 요약에서 중요한 예외가 빠질 수도 있다. 일을 나눈 만큼 전달과 검증을 신경 써야 한다.

별도 작업은 각자 완료 기준이 있고 따로 피드백하며 이어갈 일에 잘 맞는다. 검색 개선과 모바일 레이아웃 수정을 각각 진행하거나, 특정 구현 결과에 대해 별도 검증을 이어가는 식이다. 대신 초기 설명, 진행 확인, 변경 통합에 수고가 든다.

| 상황 | 적합한 방식 |
| --- | --- |
| 작은 수정이나 앞 단계의 결과에 의존하는 짧은 작업 | 에이전트 하나로 처리 |
| 한 문제를 해결하기 위한 독립적인 조사·검토 | 현재 작업의 서브에이전트 |
| 각각 완료하고 피드백할 하위 이슈 | 별도 앱 작업 |
| 독립적인 코드 변경을 동시에 진행 | 별도 작업과 worktree 검토 |
| 이슈 안에서도 탐색·검토를 더 나눌 필요가 있음 | 별도 작업 안에서 서브에이전트 사용 |

이 선택은 작업 관계와 관리 방식을 기준으로 한다. 분담으로 아끼는 시간보다 맥락 전달과 결과 통합에 드는 시간이 크면 이득이 없다. 각 에이전트가 모델과 도구를 사용하므로 전체 토큰 사용량도 늘어날 수 있다. 공식 [멀티에이전트 문서](https://developers.openai.com/api/docs/guides/responses-multi-agent#when-to-use-multi-agent)도 독립적인 일의 병렬 실행과 공유 상태를 자주 수정하는 일을 구별한다.

모델을 혼합할 때도 전달과 재검토 비용을 함께 고려해야 한다. 단순한 조사에 가벼운 모델을 쓰면 비용을 줄일 가능성이 있지만, 누락 때문에 다시 조사하거나 부모가 전부 재검토하면 이점이 줄어든다. 모델과 추론 수준을 나눠 지정할 수 있다는 사실만으로 어떤 구성이 더 경제적인지는 결정되지 않는다.

### 짧은 검토 과제에서 확인한 차이

이 구분과 별개로 속도나 비용에 차이가 있는지도 작은 코드 검토 과제로 확인했다. 같은 파일과 프롬프트로 모델·방식별 3회씩, 총 12회 실행했으며 모든 실행이 준비한 오류 5개를 찾았다.

아래는 생성 호출부터 완료까지의 시간과 API 단가 환산액의 중앙값이다.

| 모델·추론 설정 | 서브에이전트 | 별도 작업 |
| --- | --- | --- |
| GPT-5.6 Terra / medium | 41.3초 · \$0.081 | 51.1초 · \$0.085 |
| GPT-6 Astra / high | 65.3초 · \$0.265 | 79.8초 · \$0.357 |

금액은 관측한 토큰에 당시 [Standard·short-context API 단가](https://developers.openai.com/api/docs/pricing)를 적용한 값이며, 실제 Codex 청구액은 아니다. 업무를 배정하고 결과를 수집한 조율 작업의 비용도 제외했다.

이 과제에서는 서브에이전트의 완료 시간이 중앙값 기준으로 짧았지만, 생성 대기를 제외한 턴 실행 시간의 차이는 더 작았다. 캐시와 기본 지침·도구 구성을 통제하지 못했고, 비용 환산값의 반복 범위도 겹쳤다. Worktree 준비나 구현·통합, 병렬 처리량을 측정한 실험은 아니므로 이 결과만으로 작업 방식을 정하기는 어렵다. 선택 기준은 여전히 업무의 독립성과 후속 관리 방식에 있다.

## 엄브렐라 이슈와 Goal도 같은 기준으로 구분한다

현재 사용하는 구성은 엄브렐라 이슈 아래의 하위 이슈를 별도 작업에 배정하고, Goal을 설정한 조율 작업에서 전체 진행을 관리하는 방식이다. 여기에도 같은 구분을 적용할 수 있다. 이슈는 업무의 범위와 의존 관계를 정의하고, 별도 작업은 각 이슈의 실행과 대화를 맡으며, 조율 작업은 다음 업무를 배정하고 결과를 검토한다.

| 구성 요소 | 역할 |
| --- | --- |
| 엄브렐라 이슈 | 전체 범위와 완료 기준 |
| 하위 이슈 | 개별 구현·검증 범위와 의존 관계 |
| Goal을 설정한 조율 작업 | 목표를 유지하고 다음 업무를 배정하며 결과를 회수·검토 |
| 별도 구현·검증 작업 | 배정받은 하위 이슈 처리 |
| 각 작업 안의 서브에이전트 | 필요한 코드 탐색·로그 분석·검토 분담 |

Goal과 오케스트레이터도 같은 대상은 아니다. Goal은 여러 턴에 걸쳐 목표와 완료 조건을 유지하게 하지만, 이슈의 의존 관계를 실행하는 스케줄러는 아니다. 조율하는 에이전트가 이슈를 읽고, 어떤 작업을 먼저 시작할지 판단하며, 독립적인 구현·검증을 병렬로 배정한다. 실제 생성과 후속 지시에는 앞서 본 도구를 사용한다.

공식 [Goals 설명](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)에 따르면 Goal은 해당 스레드에 속한 지속 상태다. 별도 작업을 생성해도 조율 작업의 목표와 조건이 자동으로 모두 전달되지는 않는다. 각 작업에는 담당 이슈, 필요한 배경, 코드 기준과 완료 조건을 넘겨야 한다.

하위 이슈 B가 A의 결과에 의존하면 A의 완료 메시지를 받는 것만으로 충분하지 않다. A의 변경이 반영된 코드에서 B가 시작해야 한다. 검증 작업도 어느 커밋과 변경 범위를 확인하는지 알아야 한다.

개별 작업의 완료 보고 이후에도 조율 작업은 통합된 결과가 엄브렐라 이슈의 완료 조건을 만족하는지 확인해야 한다.

이 구성에 서브에이전트를 적용한다면 각 작업 안의 독립적인 조사·검토를 맡길 수 있다. 별도 작업은 이슈별 진행과 후속 대화를 유지하고, 서브에이전트는 그 안에서 필요한 업무를 나눠 맡는 역할이다. 둘 중 하나로 통일하기보다, 완료와 피드백을 관리할 단위에 맞춰 함께 사용할 수 있다.
